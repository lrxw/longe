# longe — Implementation Spec and Plan (v1)

> The folder name `.ai/` is the one thing other tooling depends on, so it stays fixed.

## How to use this document

This is both the specification and the implementation prompt. If you are a coding agent implementing this:

1. Read the whole document before writing code.
2. Implement phase by phase, in order. Stop at the end of each phase and report: what is done, what is not, what you assumed, what you need decided.
3. When something here is ambiguous, prefer the smaller interpretation and record the assumption in your report. Do not invent features that are listed under Non-goals.
4. Do not add auth, a database, telemetry, or any network call to a host other than `127.0.0.1`.

---

## 1. Purpose

A local-first, single-user board for tracking work done by AI coding agents in one repository. It solves two problems that a chat window cannot:

- **What was done, and what was decided** — durable per-topic record, versioned with the code.
- **What is waiting on me** — a central inbox of questions agents have asked, blocking ones first.

The repository's `.ai/` folder is the single source of truth. The tool is a viewer plus a thin, validated write layer that agents can use through MCP, REST, or by editing files directly.

## 2. Settled decisions

| Area | Decision |
|---|---|
| Storage | Markdown files with YAML frontmatter under `.ai/` in the project repo. Committed to git. No database. |
| Scope v1 | One repository, one working tree. |
| UI | Server-rendered HTML + htmx. No SPA, no frontend build step. |
| Agent access | MCP over **stdio** and **Streamable HTTP**, plus **REST with OpenAPI**, plus raw file access. Provider-agnostic. |
| Network | Bind `127.0.0.1` only. No auth. No outbound calls. |
| Runtime | Node 22+, pnpm, TypeScript (strict). |
| Libraries | Hono (HTTP + JSX templates), chokidar (watch), gray-matter (frontmatter), markdown-it (render), `@modelcontextprotocol/sdk`, node-notifier, Vitest. |
| Derived state | Anything not hand-authored lives in `~/.cache/longe/`, never in the repo. v1 keeps the index in memory only. |
| IDs | Topics: slug = filename stem. Questions: `q-YYYYMMDD-xxxx` (4 random base36 chars). Never sequential. |
| Timestamps | ISO 8601 with local offset, e.g. `2026-09-22T14:10:00+02:00`. |

## 3. Data model

### 3.1 Folder layout

```
.ai/
  config.yml
  topics/
    <slug>.md
  questions/
    q-YYYYMMDD-xxxx.md
  AGENT-INSTRUCTIONS.md      # generated by `longe init`, see §9
```

Everything under `.ai/` is committed. Nothing generated at runtime is written there except topic and question files created through the tool.

### 3.2 `config.yml`

```yaml
version: 1
project: My Project          # display name only
```

Keep it minimal. Statuses and transitions are fixed in v1 (see §4).

### 3.3 Topic file

`.ai/topics/<slug>.md`

```markdown
---
id: billing-refactor            # must equal filename stem
title: Billing refactor
status: active                  # see §4
created: 2026-09-21T09:00:00+02:00
updated: 2026-09-22T14:10:00+02:00
links:
  - https://github.com/org/repo/pull/42
branch:                         # reserved for future worktree support; ignore in v1
---
## Goal
One or two paragraphs. Written by the human or the agent that created the topic.

## Plan
- [x] Step one
- [ ] Step two

## Decisions
- 2026-09-21 — Chose webhooks over polling because latency matters more than simplicity.

## Log
- 2026-09-22 14:10 agent — Implemented step one, tests green.
- 2026-09-22 15:02 agent — Blocked on q-20260922-3f9a, stopping.
```

Rules:

- The four `##` sections are fixed and always present in this order. Unknown sections are preserved on write but not rendered specially.
- `Decisions` and `Log` are append-only through the tool. Humans may edit files freely; the tool never rewrites content it did not touch.
- Open questions are **not** stored in the topic file. They are rendered from `.ai/questions/` filtered by `topic`.
- "Who has the ball" is derived from `status`, not stored.

### 3.4 Question file

`.ai/questions/q-20260922-3f9a.md`

```markdown
---
id: q-20260922-3f9a
topic: billing-refactor         # optional; omit for project-wide questions
asked_by: claude-code           # free text; agent name and/or session id
asked_at: 2026-09-22T15:02:00+02:00
status: open                    # open | answered | acknowledged | withdrawn
blocking: false
options:                        # optional; 2–4 short strings
  - Keep Stripe webhooks
  - Poll Stripe API
assumption: Keep Stripe webhooks   # REQUIRED when blocking is false
answered_at:
acknowledged_at:
---
## Question
Should refunds be handled via webhooks or by polling the Stripe API?

## Context
Determines whether I need to add an idempotency table. Webhooks are already set up for payments.

## Answer
```

Rules:

- `blocking: false` **requires** `assumption`. The tool rejects the write otherwise.
- The `## Answer` section is written by the human (via UI or REST). If an option was chosen, the answer body is the option text, optionally followed by a note.
- `asked_by` is whatever the agent supplies. The tool does not verify identity.
- `reject_options` (optional, needs a topic) lists options, copied exactly, that reject the topic's reviewed work. If the human picks one while the topic is in `review`, the system moves it back to `active` (§4). The inbox shows these options in red.

## 4. Statuses and transitions

Statuses: `backlog | todo | active | needs-decision | review | done | cancelled`

Who has the ball: `backlog`, `needs-decision`, `review` → human. `todo`, `active` → agent. `done`, `cancelled` → nobody.

`backlog` is parked: agents never pick it up on their own. `todo` is the human's queue. Whenever the repo's chat is free (no turn running) and no topic is `active`, the server tells the chat to work on the oldest todo topic, the one queued first. The agent then moves it `todo → active`. Each topic is offered once per stay in todo, so an agent that does not pick it up is not asked again in a loop.

| From | To | Allowed actor | Notes |
|---|---|---|---|
| backlog | active | human, agent | Human starts it now, or the agent picks up a topic it just created (or was asked to). A human move to active through the web UI (this row, reject, reopen) also wakes the chat. |
| backlog | todo | **human only** | Queue it. |
| todo | backlog | **human only** | Take it out of the queue. |
| todo | active | human, agent | Agent picks up the next queued topic. |
| active | review | human, agent | Agent submits work. Should be preceded by a Log entry. |
| review | done | **human only** | Agents may never approve their own work. |
| review | active | human | Reject. Requires a note; written to Log as `human — rejected: <note>`. |
| review | active | **system** | Set automatically when the human answers a question on the topic with one of its `reject_options`. The note is `rejected in <question id>: <answer>`. |
| any non-terminal | cancelled | **human only** | |
| done, cancelled | active | human | Reopen. |
| active | needs-decision | **system** | Set automatically when a blocking question is created for the topic. |
| needs-decision | active | **system** | Set automatically when the last open blocking question on the topic is answered or withdrawn. |

Agents calling `set_status` with a human-only or system-only transition receive a clear error naming the rule. The same rules apply to REST and to the UI (the UI simply does not render disallowed actions).

## 5. Question lifecycle

```
open ──answer──► answered ──acknowledge──► acknowledged
 └──withdraw──► withdrawn
```

- **open**: waiting for a human. Appears in the inbox.
- **answered**: human wrote an answer. Appears in the agent's `check_answers` result.
- **acknowledged**: agent confirmed it read the answer. Leaves both lists.
- **withdrawn**: agent no longer needs it (reason appended to `## Context`). Leaves the inbox.

Side effects:

- Creating a blocking question on a topic in `active` → topic becomes `needs-decision`; Log entry is appended; desktop notification.
- Answering or withdrawing the last open blocking question on a `needs-decision` topic → topic returns to `active`; Log entry is appended.
- Non-blocking questions never change topic status.

## 6. Server

### 6.1 CLI

```
longe init   [--repo .]                   # creates .ai/ with config.yml, empty dirs, AGENT-INSTRUCTIONS.md
longe serve  [--repo .] [--port 7311] [--open]
longe mcp    [--repo .]                   # MCP over stdio; for clients that spawn a process
```

`serve` also exposes MCP over Streamable HTTP at `/mcp`, so one running process serves the UI, REST, and HTTP-MCP together.

### 6.2 Architecture

```
src/
  cli/          command parsing, entry points
  store/        read/parse/serialize topic & question files; atomic writes; id generation
  domain/       transitions, validation, derived status, side effects (pure functions)
  index/        chokidar watcher → in-memory maps; debounce; change events
  tools/        single registry of agent operations (name, zod schema, handler)
  mcp/          exposes tools/ via MCP (stdio + streamable HTTP)
  http/         Hono app: HTML routes (hono/jsx templates), REST routes generated from tools/, SSE, OpenAPI
  notify/       desktop notifications
```

Key rules:

- `tools/` is the only place agent operations are defined. MCP and REST are thin adapters over it, so both surfaces stay identical.
- Writes are **read–modify–write with atomic replace** (write temp file in the same directory, then rename). Re-read the file immediately before modifying; never write from the in-memory index.
- The watcher re-indexes on any change, including the tool's own writes. Debounce ~100 ms. Emit `topic:changed`, `question:changed` events consumed by SSE.
- Markdown rendering: markdown-it with `html: false`. Local single-user, but do not render raw HTML from files.
- All parsing errors are non-fatal: a malformed file is shown in the UI with its error and excluded from the index otherwise.

## 7. Agent interfaces

### 7.1 Tool registry (shared by MCP and REST)

Agent-facing:

| Tool | Input | Output / behavior |
|---|---|---|
| `list_topics` | `status?` | Summaries: id, title, status, updated, open question count. |
| `get_topic` | `id` | Frontmatter, the four sections as text, and the topic's questions (all statuses). |
| `create_topic` | `title`, `goal`, `plan?` (markdown list) | Creates the file in `todo`: ready work, which the todo queue picks up if the agent does not start it right away. The backlog is the human's parking lot; agents never put topics there. Returns id. Slug from title; suffix on collision. |
| `set_plan` | `id`, `plan` (markdown) | Replaces the `## Plan` section. |
| `set_status` | `id`, `status`, `note?` | Enforces §4. Appends Log entry if `note` given. |
| `add_decision` | `id`, `text` | Appends dated line to `## Decisions`. |
| `append_log` | `id`, `text`, `actor?` (default `agent`) | Appends timestamped line to `## Log`. |
| `ask_question` | `question`, `context?`, `topic?`, `options?`, `assumption?`, `blocking`, `asked_by?` | Validates (§3.4). Creates file. Applies side effects (§5). Returns id. |
| `check_answers` | `topic?` | Questions with `status: answered`, optionally filtered by topic. Includes the answer text. |
| `acknowledge_answers` | `ids[]` | Marks `acknowledged`, sets `acknowledged_at`. |
| `wait_for_answer` | `id`, `timeout_seconds` (max 300) | Long-polls the index; returns the answer when status leaves `open`, else a timeout result. |
| `withdraw_question` | `id`, `reason` | Sets `withdrawn`, appends reason to `## Context`. Applies side effects. |

Human-facing (REST and UI only; **not** exposed via MCP):

| Operation | Behavior |
|---|---|
| `answer_question` | `id`, `answer` (text) or `option_index`, `note?`. Sets `answered`, writes `## Answer`, applies side effects. |
| `approve` | `review → done`. |
| `reject` | `review → active` with required note. |
| `cancel` | Any non-terminal → `cancelled`. |
| `reopen` | `done/cancelled → active`. |

### 7.2 MCP

- Server name `longe`, one tool per agent-facing registry entry, JSON Schema derived from the zod schemas.
- Transports: stdio (`longe mcp`) and Streamable HTTP at `http://127.0.0.1:7311/mcp` (from `longe serve`).
- Tool descriptions must explain *when* to use the tool, not just what it does. `ask_question`'s description must state the blocking/assumption rule.
- Include a `resource` for `.ai/AGENT-INSTRUCTIONS.md` so clients that support resources can pull the protocol.

### 7.3 REST

- Base `/api/v1/`. One route per registry entry plus the human-facing operations. JSON in, JSON out.
- `GET /openapi.json` generated from the same schemas. `GET /api/docs` serves a minimal Swagger UI or Scalar page for manual testing.
- Errors: `400` validation, `404` unknown id, `409` disallowed transition, with a machine-readable `code` and a human-readable `message`.

### 7.4 Files

Agents may edit `.ai/**` directly. The tool tolerates this: the watcher re-indexes, validation errors are surfaced in the UI, and side effects (§5) are applied by the indexer when it detects a state change it did not perform itself (e.g. a blocking question file appearing).

## 8. UI (htmx)

All pages: minimal hand-written CSS, `prefers-color-scheme` dark/light, no framework. htmx from a vendored local copy under `public/`, not a CDN.

| Route | Content |
|---|---|
| `GET /` | **Inbox.** Open questions: blocking first, then oldest first. Each card: topic link, asked_by, age, question, context (collapsed), option buttons, free-text answer, "Withdraw" not shown (agent-only). Answering swaps the card out via htmx. Empty state: "Nothing is waiting on you." |
| `GET /board` | Columns by status in §4 order, `done`/`cancelled` collapsed by default. Card: title, updated age, open-question badge, last Log line. Click → topic page. |
| `GET /topics/:id` | Rendered Goal/Plan/Decisions/Log; the topic's questions grouped by status; status action buttons showing only transitions allowed for a human (§4); reject requires a note. |
| `GET /events` | SSE. Pages use `hx-sse` to refresh affected fragments on `topic:changed` / `question:changed`. |
| `POST /questions/:id/answer`, `POST /topics/:id/status`, etc. | htmx form targets returning fragments. Backed by the same handlers as REST. |

Title bar shows a badge: `(N) longe` where N = open blocking questions.

## 9. Agent protocol (generated into `.ai/AGENT-INSTRUCTIONS.md`)

`longe init` writes this file. The human is expected to reference or paste it into `CLAUDE.md`, `AGENTS.md`, or the equivalent for their agent.

```markdown
## Working with the .ai board

You track your work in this repository's `.ai/` folder, via the longe MCP tools
(or REST at http://127.0.0.1:7311/api/v1, or by editing the files directly).

At the start of every session:
1. Call `check_answers` and read every answer. Call `acknowledge_answers` for what you read.
2. Call `list_topics` (status: active) to see what you own.

`todo` is the human's queue: when no topic is active, pick up the oldest todo topic
(`set_status` active). Never pick up a `backlog` topic on your own: the backlog is
parked, and the human moves what should be done to todo or active. Topics you create
land in todo.

While working on a topic:
- Keep `## Plan` current with `set_plan`. Tick steps as you finish them.
- Record every non-obvious choice with `add_decision`: what you chose and why.
- When you are unsure and a reasonable default exists: `ask_question` with
  `blocking: false` and state your `assumption`, then continue on that assumption.
- When you cannot proceed without an answer: `ask_question` with `blocking: true`,
  write a Log entry saying you stopped, and stop working on that topic. Move on to
  another active topic or end the session.
- Prefer giving 2–4 `options` so the human can answer with one click.

Before you stop, for every topic you touched: `append_log` with what is done,
what is not, and anything blocked.

The human reads the board, not your terminal or chat output. Put results in the Log
and Decisions. Anything left open for the human (uncommitted work, a suggested next
step, something to check or approve) goes into `ask_question`, even when it is not
phrased as a question.

When a topic is finished: `set_status` to `review`. Never set `done` or `cancelled`;
only the human does that. When you ask the human to verify the work in review, put the
options that mean "it does not work" into `reject_options`: picking one moves the
topic back to active, and you continue there.
```

## 10. Notifications

`node-notifier` desktop notification only on a **new blocking question**: title `<project> · <the question's first sentence, without markdown>`, body `Blocking · <topic title>` (or `project-wide`). Only the server (`longe serve`) notifies; a `longe mcp` process does not, because it would report the same change again. Several within 5 seconds for one repo are sent as one, `<project> · N blocking questions`, with their headlines as the body. Topic moves (including review) do not notify; the human asked for questions only. Must never fail the operation if the notifier is unavailable.

## 11. Non-goals for v1

Auth, multi-user, multiple repositories, worktree indexing, drag-and-drop, a database, editing topic body text in the UI (only status/answer actions), `inbox/` drop folder, PLAN.md import, cloud sync, telemetry, remote binding.

## 12. Reserved for later (design hooks only)

- `branch` field on topics and questions; indexer tagging via `git worktree list`.
- Multi-repo: `~/.config/longe/repos.yml`; read-time aggregation with repo-prefixed ids.
- `.ai/inbox/`: drop a `.md`, get a topic.
- Bidirectional PLAN.md import.

Do not implement these. Do not block them either: keep ids namespaced in the index by repo path even though v1 has one repo, and keep frontmatter parsing tolerant of unknown fields.

## 13. Implementation phases

Each phase ends with passing tests and a short written report (done / not done / assumptions / questions).

### Phase 0 — Scaffold
- pnpm project, TypeScript strict, Vitest, Biome (or ESLint+Prettier), `tsx` for dev.
- CLI skeleton with `init`, `serve`, `mcp` parsing args and printing what they would do.
- `longe init` creates `.ai/` layout and `AGENT-INSTRUCTIONS.md` from §9.
- **Accept:** `pnpm test` runs; `longe init` produces the folder in a temp dir.

### Phase 1 — Store and domain
- Parse/serialize topic and question files, preserving unknown frontmatter and unknown sections byte-for-byte where possible.
- ID generation, slugging with collision suffix.
- Atomic read–modify–write helper.
- Transition table and validation as pure functions; question validation (blocking/assumption rule); side-effect computation (§5) as pure functions returning a list of writes.
- **Accept:** unit tests for every transition row in §4, both allowed and rejected; round-trip tests (parse → serialize → parse) on fixtures including odd whitespace and extra sections.

### Phase 2 — Index and watcher
- chokidar over `.ai/topics` and `.ai/questions`; debounced full re-parse of changed files; in-memory maps; typed change events.
- Derived data: open question counts per topic, inbox ordering, blocking count.
- Detect externally created blocking questions and apply side effects (§7.4).
- **Accept:** integration tests in a temp dir: create/modify/delete files, assert index state and emitted events; create a blocking question file by hand, assert the topic file is updated to `needs-decision`.

### Phase 3 — HTTP UI
- Hono app with hono/jsx templates: inbox, board, topic page, SSE, action endpoints.
- Vendored htmx. Minimal CSS. Title badge.
- **Accept:** route tests for each page returning 200 with expected markers; answering a question via the form endpoint updates the file and the returned fragment; manual smoke test in a browser.

### Phase 4 — Agent interfaces
- Tool registry with zod schemas and handlers over store/domain.
- MCP stdio server and Streamable HTTP at `/mcp`; MCP resource for the instructions file.
- REST routes and OpenAPI generated from the registry; `/api/docs`.
- `wait_for_answer` long-poll against index events.
- **Accept:** integration test using `@modelcontextprotocol/sdk` client over stdio: create topic → ask blocking question → assert topic is `needs-decision` → answer via REST → `check_answers` returns it → `acknowledge_answers` → `set_status(review)` succeeds → `set_status(done)` is rejected with the human-only error.

### Phase 5 — Notifications, polish, docs
- node-notifier hooks; failure-tolerant.
- README: install, `init`, `serve`, connecting Claude Code / Codex CLI / Gemini CLI / Cursor / Cline (stdio and HTTP config snippets), REST usage.
- `--open` flag launches the browser.
- **Accept:** fresh clone → `pnpm install` → `longe init` → `longe serve` → connect one MCP client → complete the Phase 4 scenario by hand in under ten minutes following only the README.

## 14. Testing strategy

- Unit: domain (transitions, validation, side effects), store (parse/serialize).
- Integration: index with real files in temp dirs; MCP client → server; REST via Hono's test client.
- No browser automation in v1. UI is verified by route tests plus manual smoke.
- Every bug fix adds a test that fails before the fix.
